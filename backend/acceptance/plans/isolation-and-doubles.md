# 隔离数据与外部替身设计

对应任务：E-acceptance.md"所有测试使用独立 DB/容器/端口；真实 PG 验证锁/唯一约束；
区分替身通过与真实供应商/设备通过"，以及场景清单"开始执行前准备什么"6 条。
机制入口见 `framework/isolation.py`、`framework/doubles.py`（只定机制与约定，
不连接真实库、不实现生产替身）。

## 1. 运行隔离：独立 DB / 容器 / 端口

- **原则**（COMMON.md）：测试数据库/容器/端口按 worktree 隔离；B/C/D/E 不得共享
  同一 DB 跑会清理数据的测试。
- **约定**：E 专用实例由 A 交付的镜像/部署配置 + 本包环境变量覆盖启动：
  | 项 | 约定值（样例，以 handoffs/A.md 为准） | 校验 |
  | --- | --- | --- |
  | Java Web 入口 | `E_ACCEPTANCE_BASE_URL=http://127.0.0.1:18091` | client 只接受 http(s) |
  | PG | 库名 `eaccept_*`、端口 15432（拒绝默认 5432）、低权限专用账号 | `isolation.validate_env_safety` fail-closed |
  | Worker | 独立进程/容器，指向同一 E 库 | 启动日志记 DB 名 |
  | OSS | 测试桶 + run-id 前缀对象路径，凭据仅在运行环境 | 不写入 Git/证据正文 |
  | run-id 前缀 | `E_ACCEPTANCE_RUN_ID_PREFIX`（如 `E-mvpe`） | `new_run_id` 格式校验 |
- 密码只经环境变量（PGPASSWORD 等），样例文件零真实凭据。

## 2. run-id 数据隔离与清理

- 每次 `run.sh matrix`（或单场景执行）生成唯一 run-id：`<前缀>-<UTC时间戳>-<hex>`；
  本次运行创建的一切可命名资源（虚拟手机号段、账号显示名、云台/微晶配对标识、
  任务去重键、OSS 前缀）统一带 `EACC_<hash(run-id)>_` 数据前缀。
- 并行安全：不同 run-id/worktree 前缀互不重叠；查询与断言只在自己的前缀内做，
  全局唯一约束负例（AB-04/SC-04-04）除外，其夹具用完即删。
- 清理策略（`isolation.cleanup_plan`，由持凭据环境执行）：
  1. 首选整库 `DROP DATABASE`（E 测试库允许）；
  2. 否则按前缀删除：M5 目标 → M2 云台/微晶/绑定 → M1 授权 → M4 记录/执行/方案 →
     M3 任务/报告（按外键依赖逆序）+ OSS 前缀对象；
  3. 证据 `reports/evidence/<run-id>/` 保留供审计（reports/ 不入 Git）。

## 4. 外部替身边界

- 本版外部协作者：`face_algo`（人脸匹配/质量/同人）、`llm_plan`（方案生成）、
  `push_channel`（离线/异常通知投递）、`oss`（对象存储）、`gimbal_device` /
  `microcrystal`（真实硬件，联调项）。
- **替身只能经 A 的适配端口注入**（A-foundation 范围 4："明确隔离的测试替身；
  生产配置缺能力时 fail closed"）。E 包不实现任何生产替身、不另造端口、
  不测内部函数；`doubles.py` 只做声明登记与证据分级。
- 无 A 替身能力时相关场景仍 dependency_pending，不以自建 mock 冒充"集成已通过"。

## 5. doubles_pass / real_pass 区分规则（`framework/doubles.py`）

- 每场景执行前提交 `DoublesManifest(scenario_id, usages)`：每个外部依赖标
  `double` 或 `real`。
- 结论标签按**最保守口径**：
  - 全部关键依赖 `double` → `doubles_pass`（业务分支验证有效，但禁止写"算法准确率/
    设备已停止/手机已收到"类结论）；
  - 全部 `real` 且有真实观察证据（供应商回执、设备观察、手机截图）→ `real_pass`；
  - 混合 → `mixed`，报告逐项注明哪部分未真实；
  - `assert_claimable("real_pass")` 在含替身时抛错——代码级防冒充。
- 清单硬约束（原文）：模拟通过不能代替真实设备停止、人脸连续性或手机实际收到通知；
  `REAL_ONLY_CHECKPOINTS` 列出这些必须真实证据的结论。

## 6. 真实 PG 验证锁/唯一约束的安排

内存替身不能证明锁与约束，以下必须在 E 专用**真实 PG** 上执行（A 基线后）：

| 验证点 | 场景 | 方式 |
| --- | --- | --- |
| 同微晶双控制端原子占用（行锁/唯一索引） | SC-04-04、SC-07-05 | 并发 ≥2 路 M4-A03，断言至多 1 成功且 PG 仅 1 行占用 |
| 记录去重唯一约束（同键同内容一次、异内容冲突） | SC-02-04、SC-02-09、SC-06-02 | 并发 M4-A05 批次 + 唯一索引违例路径 |
| 云台唯一当前任务（替换原子性） | SC-R-08、SC-R-13 | 并发 M3-A01 与 M4-A03，查当前指针无中间态 |
| 绑定唯一/防覆盖 | SC-01-05、SC-R-02、SC-R-05 | 并发 M2-A06/M2-A08，真实唯一约束拒绝 |
| 租约过期重领、旧代次回写拒绝 | SC-C-03、SC-C-04、AB-07 | kill worker 后观察任务表状态机 |

执行时并发窗口用真实 HTTP 客户端线程池制造；SQL 侧只读核对（写入边界归 A 的
Web/Worker 划分，E 不直写业务表——清理例外，走第 2 节策略）。
