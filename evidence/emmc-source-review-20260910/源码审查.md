# eMMC 读取路径静态审查

本轮从已下载官方 SDK Git 对象库提取四份参考源码，逐份核验 Git blob SHA-1，另记录 SHA-256，见 manifest.json。未访问硬件、未编译或替换 U-Boot。

## 发现

- Linux `sdhci-of-dwcmshc.c` 和 U-Boot `rockchip_sdhci.c` 均有明确的 `rockchip,rk3576-dwcmshc` 匹配项。不能把无线 SDIO 的 DWMMC 驱动直接视为 eMMC 驱动。
- U-Boot `sdhci.c:71` 的 `sdhci_transfer_data()` 使用计数超时，正常路径约 1000000×10 微秒；但 ready 中断置位且 PRESENT_STATE 无数据可用时直接 `continue`，绕过下面的超时递减。若此状态持续且 DATA_END 不置位，循环缺少有效截止条件。这是静态可达的无界等待风险，不是已确认的实板根因。
- `part_efi.c` 通过 `blk_dread()` 读取 MBR、GPT 头及分区项，因此上层分区查询依赖底层读传输能返回。尚未证明正在运行的 U-Boot 二进制与此 SDK 源码完全一致，也未捕获卡住时控制器寄存器。
- RK3576 HS200/HS400 的 TX/CMD/strobe 参数两套源码分别有配置。特别是 ddr50_strbin_delay_num 在 U-Boot 为 16、Linux 为 10；不能不看时钟路径就混用参数，更不能据此认定某个值错误。

## 下一步实现约束

原生 openvela 首阶段应做有界、只读、低速单块 PIO 读取入口：所有分支使用同一个单调时钟截止时间，超时记录命令、PRESENT_STATE、INT_STATUS 并返回；禁止内部无限重试。初期排除 DMA、HS400 调谐、写块和自动挂载。先补齐时钟/复位/电源及控制器接管条件，再安排 RAM 固件验证。完成后才进入分区解析和只读文件访问。

本轮没有重跑此前会无回应的 `mmc part`，没有写 eMMC。当前仍不能宣称原生 eMMC 文件读取已完成。
