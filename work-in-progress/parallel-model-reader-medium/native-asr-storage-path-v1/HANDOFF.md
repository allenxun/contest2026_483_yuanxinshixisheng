# First native ASR ordinary-file path

Recommended eventual path: /mnt/k7model/encoder.ort and /mnt/k7model/decoder.ort, with the matching tokens.txt and a trusted expected-length/SHA256 manifest. These are proposed paths, not observed files. No evidence establishes that the inserted USB drive currently contains these models or any suitable filesystem. No eMMC write, format, partition change or PC inference is needed for this design.

What is actually established: evidence/usb-readonly-20260910/runtime-acceptance.json records the earlier usb-readonly RAM image, /dev/sda enumeration,512-byte sectors,60555264 sectors, two equal LBA0 reads CRC32 b1241e76 and successful close. read.bin records boot_signature=1, exfat_oem=0. That does NOT distinguish an MBR from a FAT volume boot sector, prove a valid FAT partition, or rule out exFAT in a partition. It is historical evidence, not a fresh assertion about today's firmware/node identity. VID/PID/strict media identity were not recorded. filesystem_mounted=false and model_loaded=false.

app/k7storage/k7storage_main.c:68 onward opens a blockdriver directly, checks read-only geometry and performs two sector reads. It has only start/list/read commands, no mount/file transfer/model reader. A working /dev/sda block node is NOT an ordinary model filename and must not be passed to Sherpa or model_reader. USB bulk reads concurrent with audio/ASR are not validated by that two-sector test.

FAT already has a bounded integration candidate in formal source: app/k7fat/k7fat_main.c:8 requires CONFIG_FAT_FORCE_READONLY, CONFIG_USBHOST_MSC_READONLY and CONFIG_FAT_FORCE_INDIRECT; its mount command:64 uses /dev/sda -> /mnt/k7model, type vfat, MS_RDONLY. It allows one mount attempt per boot, lists at most64 entries, and retains uncertainty on failed close/unmount. evidence/build/fat-readonly-20260910/verification.json records build_exit_code0 but hardware_tested=false. The old docs' 'not integrated' statement is superseded for source/build presence, NOT for runtime mount acceptance. Current FAT-disabled profile cannot expose USB files via that mount.

Minimal next steps for root, sequentially:

1. Keep current model/ASR work separate from disk mutation. Inventory the presently attached USB media read-only and bind it to the new USB block node; do not assume /dev/sda from yesterday, nor treat node spelling as identity. Determine actual FAT-compatible volume/partition through bounded read-only inspection. If unsupported/unknown, stop that mount attempt; do not format or write a partition table. Existing k7fat is fixed to sda: an actual different node/partition requires a narrowly reviewed binding change, not a guessed command.
2. Integrate the already built FAT read-only source into the current ASR firmware profile: CONFIG_FS_FAT=y, CONFIG_FAT_FORCE_READONLY=y, CONFIG_FAT_FORCE_INDIRECT=y, existing MSC READONLY=y, EXAMPLES_K7FAT enabled, mountpoints available. Keep FS_LARGEFILE=y for reader's64-bit off_t requirement. Preserve FAT write-denial at filesystem and MSC layers; MS_RDONLY alone is insufficient. Keep default LFN-off only if names use8.3: encoder.ort, decoder.ort, tokens.txt all qualify. Do not introduce long model directory names without LFN configuration. Rebuild/boot is root work; old FAT build is not proof of current combined image.
3. Model transfer is still missing. Establish whether the exact files already exist; do not infer from USB presence. If absent, arrange an explicitly authorized transfer of the already frozen files and token table to suitable removable media using a separate host/media preparation step, then safely return it to the board. That is byte transfer, not PC inference. This report performs no transfer and authorizes no format/eMMC write. A network-to-RAM transfer alternative would require a real bounded receive/storage path that is not provided by k7storage, so is not the shortest proven route.
4. First real file gate: mount read-only, list, stat/fstat regular files, check exact sizes and read/seek/close behavior on a small known file; then stream-hash complete encoder/decoder/tokens against the trusted manifest on board. Converted encoder166189616 bytes and decoder72024848 bytes are individually well below FAT's UINT32_MAX file-size limit. tokens identity must be frozen separately; no claim that it is installed. Record mount/volume identity and keep it mounted and physically stable until all loading finishes.
5. Connect the verified byte source to the actual Sherpa load owner; keep filename allowlist/expected lengths and errors explicit. app/k7agent/model_reader is existing bounded reader code, not an automatic Sherpa interceptor. Do not enable MR_POSIX_TRUSTED_FILES solely because FAT mounts: model_reader.c:105–120 requires64-bit off_t, O_NOFOLLOW/O_NONBLOCK, regular-file checks and trusted ancestors. FAT st_dev/st_ino are zero, so equality does not prove file identity or prevent media swap. Its default ENOTSUP gate must be resolved through a reviewed trusted-volume/lifetime policy, not bypassed with /dev.

For this ASR path the relevant separate gap is Sherpa ReadFile -> std::ifstream -> vector -> ORT Session, identified in native-kaldifst-no-pipe-v1: it does not use mr or its integrity owner. Hashing an fd and then reopening by path is not same-handle verification. Prefer hashing the exact bytes retained for ORT Session construction, or wire the existing checked reader into that one buffer-fill owner; the root must budget the whole model-vector plus Session weights. Do not copy the old llama-specific reopen patch into Sherpa. No reader implementation or broad loader rewrite is part of this report.

Current conclusion: USB bounded block reading has historical device evidence; forced-readonly FAT has source and target-build evidence; ordinary USB model files, mount compatibility, full-file integrity, current combined firmware and actual ASR loading are still unverified. This report only reads source/archived evidence and freezes hashes, without filesystem/device/SDK operations.
