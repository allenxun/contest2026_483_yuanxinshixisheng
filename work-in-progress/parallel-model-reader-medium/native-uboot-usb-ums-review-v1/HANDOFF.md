# Future U-Boot external-USB UMS transfer: not yet demonstrated

Conclusion: the proposed route is conditional, not currently a proven replacement for mw.q. This review did not interrupt the active serial transfer, access a serial/device node, run SDK commands, write removable media, or download anything.

Direct archived evidence: evidence/resource-audit-20260910/live-uboot.json contains successful bdinfo, fdt inspection and mmc list. It identifies mmc@2a330000:0 as eMMC. It does NOT contain help ums, help fatload, help usb, successful UMS gadget enumeration, or USB-backed UMS operation. Searches of archived evidence text/log/bin found no ums/fatload command evidence. The locally frozen U-Boot reference set under evidence/emmc-source-review-20260910 is MMC-related; no cmd/usb_mass_storage.c or f_mass_storage.c was located in this workspace search. Therefore the installed U-Boot's accepted UMS interface types and exact command grammar cannot be certified here. Do not execute an Internet example such as 'ums 0 mmc 0': the archived mapping makes that an eMMC exposure risk.

The earlier NuttX USB proof is a different software stack: usb-readonly runtime recorded /dev/sda,512-byte sectors,60555264 sectors, two equal LBA0 reads. It cannot establish U-Boot usb storage support, its device index, or the same controller's host/gadget concurrency. /dev/sda is not a U-Boot device selector. Current user/root statement is Windows enumerates CH340 COM8 and no VID2207: that establishes no observed2207 gadget at that observation, not that an OTG cable is absent. A gadget need not be active before entering its mode, and this review has no verified installed U-Boot gadget VID/PID contract.

Required capabilities before any export:

- Installed U-Boot has an enabled UMS command whose backing block device can be the 'usb' interface, not only mmc; its concrete source/command help must confirm this. Merely having 'ums' listed does not prove arbitrary block interfaces work in this fork.
- USB host enumeration identifies the EXTERNAL drive by controller/port, manufacturer/model/serial if reported and capacity/partition metadata. Map its U-Boot index independently; never infer from NuttX or Windows indices. Capacity alone is not unique identity.
- A separate usable gadget/peripheral connection to Windows, with data cable and correct controller role, must coexist with the host controller serving the flash drive. A dual-role controller switching from host to gadget could remove its own backing device; topology/driver evidence is necessary. Current snapshots do not prove concurrency or connector routing.
- The drive contains a compatible readable/writable filesystem for the Windows transfer and later U-Boot fatload; observed boot signature and exfat_oem=0 at LBA0 do not prove this. Partition-aware inspection is missing. No formatting/repartitioning is proposed.

Future parent-owned gates AFTER the active load finishes and only when another U-Boot session is appropriate: first archive 'help ums', 'help usb', 'help fatload' output and boot version. Then use only documented read-only host enumeration/storage/partition listing commands to bind the external USB device. Do not probe eMMC or repeat the previously problematic mmc part. Review exact controller and backing-interface syntax from that help/source before forming an export command; this report deliberately provides no ready-to-run UMS command with guessed selectors.

Only after external-drive backing is unambiguous may a separately authorized UMS export be considered. On Windows bind the newly appearing disk to its arrival event and USB identity/capacity/partition, preserving existing volumes; refuse format/repair prompts. UMS exports block media, so filesystem metadata writes can occur in addition to requested model/firmware file writes. Never expose eMMC to get around an unsupported USB-backed path. Write exact existing files with before/after host hashes, safely eject/flush Windows, then terminate UMS by the installed command's documented mechanism. Avoid simultaneous U-Boot filesystem access while Windows owns the exported media.

After ownership returns, independently list files and use the installed fatload grammar against the verified USB device/partition and a root-reviewed RAM address/range. Check loaded byte count and hash using only commands actually available. FAT load into RAM avoids persistent boot media writes, but its destination must not overlap U-Boot relocation/stack/FDT/reserved memory/current image; archived bdinfo is not sufficient to choose a universal address. No saveenv, flash write, partition mutation or guessed execution entrypoint is included.

If USB-backed UMS or host/gadget concurrency is absent, the bounded fallback is physically preparing the external drive on a host, then returning it to the board and verifying U-Boot USB/FAT read support. That is file transfer, not PC inference. It still needs device handling authorization and demonstrated fatload support. Current long mw.q load must finish without interference; all alternatives are for future sessions.

Frozen inputs are listed in inputs.json. This is a capability/identity gap report, not a speed estimate, successful UMS test or firmware modification.
