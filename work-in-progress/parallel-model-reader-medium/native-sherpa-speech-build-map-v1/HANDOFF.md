Use the upstream full core source list instead of inventing a hand-trimmed list that omits registry/constructor references. ## VITS and rule.far

ENABLE_TTS=ON appends offline-tts-vits-model/config and TTS implementation/text processing sources and links cppinyin_core and piper_phonemize (csrc:312+). Top-level:400–405 includes cppinyin, espeak-ng-for-piper and piper-phonemize whenever TTS is enabled, even if this particular model chooses a lexicon frontend. Record/build these real upstream dependencies first or separately review a model-specific frontend cut; do not silently drop link targets.

Existing model configuration is vits-icefall-zh-aishell3/model.onnx + tokens.txt + lexicon.txt + rule.far. offline-tts-vits-impl.h:53–78 opens each configured FAR with fst::FarReader<fst::StdArc>::Open, copies/converts contained FSTs to StdConstFst, and constructs kaldifst::TextNormalizer. This requires real fstfar/fst and normalizer support and ordinary resource files; rule.far is not an ONNX initializer and not covered by the ONNX graph inventory. Removing it changes normalization behavior. Its prior size180717014 bytes does not equal runtime memory; parsing/copying FSTs adds storage and needs target measurement. Lexicon frontend selection depends on actual model metadata/config in :390–427; TTS=ON compilation includes other frontend paths irrespective of which branch this model takes.

FAR is an existing prebuilt model asset: no FST compiler is needed just to read it. If rebuilding rule archives later, use separately version-locked host generators; never run an ARM64 target build tool on the host, and never treat a host output as native executable code. eSpeak/piper may have their own data-generation steps: inspect their fetched fixed-source build before cross-compiling; current recipe locks alone do not prove host/target generator separation. No new generator is run here.

## NuttX integration procedure

asr-initial-cache.cmake disables binaries/examples/PortAudio/WebSocket/Python/JNI/GPU/RKNN/diarization/tests and TTS for first ASR library. Configure a separate TTS-enabled build after ASR gate, preserving ABI. Supply real NuttX ARM64 C/C++ toolchain and verified source overrides for the exact FetchContent names in dependency-recipes.json; disconnected mode alone does not verify provenance. Avoid implicit mirror downloads.

Required small integration gap before configure: top-level includes cmake/onnxruntime.cmake unconditionally at374. Its preinstalled search may find a host or Linux library, and its download branches are platform archives. For NuttX, root must bypass that recipe only when a real already-built ORT target/complete imported static target closure and target API include directory are supplied. csrc:291–296 already links TARGET onnxruntime if present, otherwise raw onnxruntime_lib_files. Prefer supplying a genuine onnxruntime interface/static target with the complete normal-demand dependency closure; an empty target or a single incomplete archive is invalid. Do not set CMAKE_SYSTEM_NAME=Linux to select packages. This map does not supply a fake target or enable that bypass automatically.

csrc adds -lm for non-Windows; retain actual NuttX/toolchain math resolution. Its -ldl/-pthread additions are Linux-only, so NuttX must obtain actual thread/runtime symbols from target build integration without fake libraries. Do not use the libstdc++ static flag with NuttX libc++ accidentally. Keep ordinary model reads, C++ runtime/exception flags and static object ABI consistent; no CPU affinity claims.

Acceptance after build: real C API recognizer with encoder/decoder/tokens,16k feature80,CPU1 and greedy search matches existing source-model configuration; real TTS with model/tokens/lexicon/FAR uses model-declared sample rate (prior metadata8k), not assumed16k. Both require native runtime validation, memory/failure behavior and VoiceLink API connection. Nothing in this deliverable represents ASR/TTS execution or deployment.
