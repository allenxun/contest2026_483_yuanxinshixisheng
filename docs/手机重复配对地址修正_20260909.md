# 手机重复配对地址修正

## 现场触发与结论边界

用户修正蓝牙调试器 TX=0003、RX=0002 后，日志出现通知描述符写入，但重新配对连续失败，设备发送 `RADIO SMP TX failure reason=4`。用户确认又出现两三秒自动断开。

上一版 `phone-pairing-20260909` 的首次手机加密与至少 100 秒保持连接确实通过，但重复配对仍失败，不能将初次成功写成稳定性验收通过。记录容量修正解决一项限制，并未解决本次确认值校验错误。

现场证据：`evidence/phone-pairing-20260909/phone-observation-03.jsonl`，尤其 15:46:06、15:46:10 的发送方向失败码 0x04。通知订阅与加密是独立条件，订阅成功不能跳过失败的配对。

## 源码原因与修正

旧 `bt_hcicore.c` 在连接完成后调用 `copy_id_addr()`，使用先前收到的 IRK 将手机的可解析随机地址转换为身份地址，并保存在 `conn->dst`。但是 `bt_smp.c` 生成与验证 Legacy Pairing 确认值时也使用 `conn->dst`。这样在已识别身份的手机发起新配对时，设备与手机可能使用不同地址计算 c1，导致确认失败。

蓝牙规范要求确认计算使用建立连接时的地址，见 [Bluetooth Core Security Manager Specification，2.3.5.5](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/security-manager-specification.html)。源码分析确定上述地址混用缺陷，实际故障修复仍需重复配对真机验证。

修正包含三个源码文件：

- `bt_conn.h`：增加 `dst_on_air`，保存本次连接原始对端地址及类型。
- `bt_hcicore.c`：在身份解析前保存 HCI Connection Complete 中的原始地址。
- `bt_smp.c`：生成和验证确认值都调用同一个地址选择函数，使用 `dst_on_air`；身份地址仍用于配对记录查找。保留加密要求。

源码位于统一项目 `port/tracked/nuttx/wireless/bluetooth/`。当前 K7 使用本机公共蓝牙地址发广播，`conn->src` 仍对应实际本机地址；本修正不宣称实现此前未支持的本机隐私地址切换。

## 验证与镜像

`tests/bluetooth/test_pairing_addresses.c` 通过工具提取并执行生产源码中的实际地址选择函数，使用不同的随机地址、身份地址和地址类型，覆盖中心/外设两种角色、已有身份解析和首次配对，确认身份记录没有被改变。ASan/UBSan 测试通过；另核对连接完成时的地址保存发生在身份解析之前，两个确认路径均使用新函数。

独立构建目录：`cmake_out/velavision_phone_rpa_20260909`。

镜像版本：`phone-rpa-20260909`，构建通过；SHA-256：`a615790446aba99a8ee1252e55de5ec83c9b5902772b94a103fff06e18118ae2`。构建证据在 `evidence/build/phone-rpa-20260909/verification.json`。入口和 6 MiB RAM 预留范围已核验。

后续已完成 RAM 加载与启动，无线模块返回 Wi-Fi/BT 就绪，配网服务返回 `receive_credentials=1 connect=0 advertise=0`，`bt-host ret=0`。证据在 `evidence/phone-rpa-20260909/`，当前只读观察 PID 文件 `private/rpa-watch-01.pid`，占用 COM8 最长 1800 秒。此时手机重新配对及 X 业务收发仍待现场验证；没有刷 eMMC，没有启动云台。
