# Wi-Fi 完善：ARP 等待与联调诊断

本轮固件 `wifi-arp-20260909` 已独立编译通过，尚未上板。COM8 可打开，但状态命令超时，发送换行后 3 秒接收字节数为 0；等待用户确认供电和串口连接。不能写成 ARP 首包问题已经修复。

## 改动与依据

- `board/kickpi_k7/configs/velavision_wifi_ip_local/defconfig`：ARP 单次等待由 SDK 默认 20 ms 改为 250 ms，保持 5 次重试上限。SDK `nuttx/net/arp/Kconfig` 明确说明应按网络最大往返时间选取等待值；先前网关实测常见 36–120 ms，20 ms 偏短是可验证的原因假设。
- `app/k7radio/skw_netdev.c`：增加 ARP 请求、回复收发计数和实际等待配置输出。发送计数表示发送接口返回成功，不等于空口交付或收到路由器回应。
- `app/k7radio/prov_service.inc`：保留最近一次命令类型、事务 ID、session、处理返回值、Notify 返回值，不保留 SSID、密码或完整请求。`command=3` 为 connect，`command=4` 为旧 submit_credentials。
- `frontend/vela-provision.mjs`：scan() 先查询真实状态，在线时返回 online_scan_unavailable；status() 匹配会话，避免旧会话回包误用。原始 X 的板端在线扫描限制仍在，没有伪造列表或断网扫描。
- `frontend/接入示例.mjs`：遇到已联网不能扫描时，保留 BLE 连接和真实 IP，避免扫描页错误处理直接关闭 BLE。

## 恢复板端后如何验收

1. 先确认实际运行环境与供电，核对新镜像哈希，从 RAM 加载；不刷 eMMC/STM32，不启动云台。
2. 经加密 BLE 提交真实 connect 请求，匹配 wifi_connecting、wifi_connected/IP 与 status。
3. 查询网关 ARP 项并执行有界首包测试，对照新增 ARP 请求/回复计数；检查是否仍出现 sendto errno 101。必要时明确删除本机该网关的缓存做冷邻居测试，保留每次失败，不只挑成功轮次。
4. 再验证在线 scan() 的前端提示不会关闭 BLE；后续单列长时间保持、错误密码及断线恢复测试。

本轮不宣称完成 DNS/互联网、WPA3/企业网、在线扫描、凭据持久化或自动重连。这些仍是后续工作。
