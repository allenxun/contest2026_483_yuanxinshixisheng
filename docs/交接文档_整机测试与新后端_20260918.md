## 推荐的上板测试顺序

### A. 恢复并确认固件

1. 单独保留一个串口所有者；关闭或停止旧联调窗口，避免抢 `/dev/ttyUSB0`。
2. 保持 QinHeng/CH340 串口接 Ubuntu。
3. 让板子进入 Fastboot，并在 VMware 把 **USB download gadget** 连接到 Ubuntu；不要凭 Windows 设备管理器的名称判断是否成功。
4. 执行 `tools/load_photo_foreground.py --load --run-label <本轮标签>`。
5. 加载后只读核对 `nsh`、无线服务、`k7cloud` 命令和版本/CRC；确认后再让 App 配网。
6. 接入 `openvela link probe`，确认 `/dev/video*` 和实时帧，再启动联调窗口。

### B. 新后端单轮闭环

1. App 重新连接 BLE 并提交 Wi-Fi，确认板端获得 IP；记录新 IP 和时间。
2. 先确认相机视频新鲜、云台在 0/0、环境无遮挡；没有用户准备确认时不要录音或移动。
3. 进行一轮真实命令：唤醒 → 云台跟随 → 皮肤检测 → 正面/左侧/右侧三图。
4. 记录每张 JPEG 的大小和哈希，不保存原图到公开证据。
5. 由网关用新环境上传，检查 `accepted=true`、`status=queued` 和新 `taskId`。
6. 轮询 `GET /api/v1/skin-assessment-tasks/{taskId}`：`queued/analyzing` 继续等待，`needs_retake` 按 `requiredViews` 补拍，`failed` 记录 `failureCode`，`report_ready` 取 `reportId`。
7. 用同一设备 Bearer token 请求 `GET /api/v1/skin-reports/{reportId}?view=brief`，把真实 brief 内容分段送 TTS；不要播放联调声明或 mock 文案。
8. 报告播放完成后确认软件恢复和实体云台跟随；两者都要记录，软件日志单独的 `result=0` 不足以证明电机动作。

### C. 稳定性验收

只有基线同时满足才开始计时：预览新鲜、Wi-Fi 新鲜回包、BLE 已连接且加密、串口无错误、内存读数持续更新。

- 两小时：同一串口所有者每分钟采集 BLE/Wi-Fi/内存/视频遥测；断链、状态过期、视频停滞或串口错误立即保留失败，不自动重连掩盖。
- 十轮：每轮必须有真实唤醒、实际跟随、三图同一 epoch、后端新 taskId、真实报告分段播放和回到待机；不得把重复 epoch 算新轮次。
- 异常恢复：单独时段测试 Wi-Fi 短断、手机 BLE 重连、后端暂不可达；每项记录检测、提示、恢复耗时和是否需要人工干预。
- 延迟：按“语音结束→命令应用/提示起播”“照片保存→本地提示起播”“上传开始→ACK”“report_ready→首段起播”记录样本数、中位数和最大值。

验收计划详见 `docs/整机稳定性验收_20260917.md`。此前两小时和十轮均未通过，不能从历史两组三图推算通过率。
