## 1. 当前目标与已经冻结的产品流程

近期目标是尽快跑通整机联调：

1. 手机或前端通过加密 BLE 连接 K7。
2. K7 扫描 Wi-Fi，前端显示列表。
3. 用户在前端选择 SSID 并手动输入密码。语音不再输入 Wi-Fi 密码。
4. K7 完成 WPA2、DHCP，向前端回报 `wifi_connected` 和 IP。
5. 板载喇叭播放本地预生成男声“联网成功”。这一步不能依赖云端。
6. 分开确认互联网和云端门禁：Wi-Fi、IPv4、DNS、熵源、可信时间、CA、TCP、API 配置共八项。
7. 门禁全部通过后，联网语音使用小米 MiMo `mimo-v2.5-asr` 和 `mimo-v2.5-tts`。
8. 再将云语音与业务后端设备会话、心跳、状态、测肤任务和报告接口整合。

不要恢复“全离线语音说密码”的旧主线。旧 Paraformer/VITS 代码和证据继续保留，用于提示音、离线回退和问题追溯。

## 5. 音频合同

- 批式 ASR：WAV 内部必须是 PCM16LE、16 kHz、单声道；板端也可提供同格式裸 PCM，候选代码会包装 WAV。
- 规划的流式 ASR：裸 PCM16LE、16 kHz、单声道，20 ms 一帧，即 320 samples / 640 bytes；连接起始发送一次元数据，每帧有 seq/timestamp，结束发 EOF。不要给每个音频帧重复 WAV 头。
- MiMo TTS 常见输出：PCM16 WAV、24 kHz、单声道。
- K7 播放目标：裸 PCM16LE、16 kHz、单声道。
- 当前 24→16 kHz 是有界批式功能转换；需要更好的音质和响应速度时再实现带低通的有状态流式重采样。

真实 MiMo 连通性曾在主机进程内做过：TTS“你好联网”生成约 1.173 秒 24 kHz WAV；ASR 接受重采样后的 16 kHz WAV、响应约 658 ms，但合成样本识别文本不正确。这只能证明账户、模型和协议可达，不能证明真实麦克风准确率或板端调用成功。证据位于 `evidence/integration-api-20260914/mimo-live-*`，不要重新保存 key。

## 8. OTG、串口和安全边界

- 大镜像统一优先 OTG Fastboot RAM 传输；串口只做控制、CRC 和日志。
- 不得静默回退到串口逐条 `mw.q` 传大镜像。
- 本轮不刷 eMMC、不写 STM32、不启动云台、不远程 push。
- `RAM-only` 不等于断电保留；复位后旧模型 CRC 可能失效。

Windows/VMware 的 OTG Code 43 已多次复现。相同故障不要只循环重启 VMware USB 服务或拔插线，按已成功流程：

1. 先恢复 QinHeng/CH340 串口。
2. 通过板端软件 reset，拦住自动启动进入 U-Boot。
3. 重新校验仍需复用的 ASR/TTS RAM 区 CRC；复位后不沿用旧 CRC。
4. 执行 `fastboot usb 1`。
5. 确认 Windows 中设备正常枚举为 `USB download gadget`。
6. 再在 VMware 可移动设备中接入 Ubuntu。

USB 代理恢复只是当轮可用，不得写成永久硬件修复。涉及板端状态的任何结论都要保存串口/CRC/哈希证据。
