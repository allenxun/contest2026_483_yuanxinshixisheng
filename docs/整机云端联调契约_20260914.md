## 2. 联网到云端的状态机

```text
OFFLINE
  -> WIFI_ASSOCIATED
  -> IPV4_READY                 已取得非 0 地址、网关、DNS server
  -> DNS_READY                  正式 hostname 至少解析出一个可用 IPv4
  -> TLS_READY                  SNI/证书链/hostname/时间校验全部通过，flags=0
  -> GIMBAL_SESSION_READY       POST /api/v1/gimbal-sessions 成功
  -> CLOUD_ONLINE               心跳被接受，或受控业务请求成功
  -> SPEECH_READY               后端新增 ASR/TTS 后才能进入
```

任一步 Wi-Fi link loss、地址失效或取消都必须关闭在途 socket 并退回 `OFFLINE`。DNS 失败不能直接改用未授权固定 IP；TLS 失败不能降级到 HTTP。设备 session 返回 `401 SESSION_INVALID` 时退回 `TLS_READY` 并重新握手，不能复用旧 token。

`GIMBAL_SESSION_READY` 与“绑定到某个 APP 账号”是两件事。云台设备凭据换得 device session；APP 另用自身 session 和 pairing proof 执行绑定。请求体不能自报 `accountId` 或 `gimbalId` 来改变主体，主体只从 token 派生。

## 3. 通用 HTTP 约定

除下表显式标为公开的接口外，全局安全方案为 HTTP Bearer：

```http
Authorization: Bearer <APP session token 或 gimbal device session token>
```

主体类型和资源可见性由端点运行时校验；仅带 Bearer 不代表 APP 可以调用云台专属接口，或云台可以访问任意任务。

普通成功响应为：

```json
{
  "requestId": "每次 HTTP 尝试的新 ID",
  "data": {},
  "meta": {
    "replayed": false,
    "serverTime": "2026-09-14T00:00:00Z"
  }
}
```

错误响应为 `{requestId,error:{code,message,retryable,details?}}`。每个响应含 `X-Request-Id`；`204` 无 body。`requestId` 不能当幂等键。除设备握手和按 `observationEpoch + observationSeq` 排序的心跳外，业务写请求要求 `Idempotency-Key`（1—128 字符）。同键同内容返回原结果并令 `meta.replayed=true`；同键异内容为 `409 IDEMPOTENCY_CONTENT_CONFLICT`；处理中为 `409 REQUEST_IN_PROGRESS`，客户端按 `Retry-After` 用同一键重试。

`ErrorEnvelope` 的 `requestId` 和 `error` 为响应主体；`ErrorBody` 含稳定 `code`、仅供人阅读的 `message`、布尔 `retryable` 和可扩展的可选 `details`。客户端只按 `error.code` 分支并容忍 `details` 新增键。当前只有 `REQUEST_IN_PROGRESS`、`RATE_LIMITED`、`DEPENDENCY_UNAVAILABLE`、`DEPENDENCY_TIMEOUT` 为可原逻辑重试；前两者遵守 `Retry-After`，依赖类采用有界退避。

JSON 中 bigint、revision、seq、版本号均为无符号十进制**字符串**，不能按 JSON number 编解码。时间为 RFC3339 UTC 秒精度。

### 4.1 设备会话和心跳 schema

`GimbalSessionRequestBody` 必填：

- `credential: string`，最长 256；具体格式和预置方式尚未冻结。
- `credentialVersion: string`，无符号 bigint 十进制字符串。
- `proof: string`，最长 512；nonce/proof 算法尚未冻结。

`GimbalSessionData` 必填：`gimbalId`、`sessionToken`、`expiresAt`、`serverTime`。`sessionToken` 用于后续 device Bearer，禁止写日志。

`HeartbeatBody` 必填：

- `observationEpoch: string`，1—128 字符；同一 generation 内保持不变并跨 token refresh / 进程重启持久化。
- `observationSeq: string`，同一 generation 和 epoch 内严格递增。
- `observedAt: date-time`。
- `powerState: awake|asleep`。

可选 `taskId`、`executionId` 和 `incidents[]`。这两个 ID 只是观察值，不能移动当前任务指针或制造业务成功。`HeartbeatAck={accepted,lastSeenAt,statusRevision,serverTime}`；旧序号也返回 `200`，但 `accepted=false` 且不得推进状态。

`StatusView` 的固定字段为 `connectionStatus: unknown|online|offline`、可空 `powerState`、可空 `lastSeenAt`、`isStale`、`statusRevision`、`incidents[]`。`isStale=true` 时不能把投影描述成实时在线。

### 4.2 绑定 schema

`BindingStatusView={bindingStatus: unbound|self|other,bindingRevision:string}`。查询绑定状态额外要求 `X-Pairing-Proof`；缺失/空白是 `400`，验证失败是 `403`。

`BindingBody` 必填：

- `expectedBindingRevision: string`，无符号十进制字符串，首次为 `"0"`。
- `pairingProof: string`，最长 8192；证明格式仍待设备协议冻结。

`BindingResultView` 必填 `bindingStatus`（成功恒为 `self`）、`gimbalId`、`bindingRevision`、`boundAt`。

### 4.3 新建测肤任务

`POST /api/v1/skin-assessment-tasks` 使用 `multipart/form-data`：

- `metadata` 的 part Content-Type 必须是 `application/json`，schema 为 `A01Metadata`。
- `front`、`left`、`right` 三个 binary part 全部必需，不得少传、多传或重复。
- `A01Metadata` 必填 `photoVersion: "1"`、`captureSessionId`（1—128）、`consentEvidenceRef`（1—128）。
- 图片按内容嗅探，仅接收 JPEG/PNG/GIF/WebP；OpenAPI 开发初值为单图不超过 10 MiB，三图合计不超过 32 MiB。

`202` 只表示异步任务已受理。`AssessmentTaskAccepted` 包含 `taskId`、固定 `status=queued`、`photoVersion` 和可空 `currentAssessmentRevision`；不能把它当成分析或报告成功。

### 4.4 补拍

`PUT /api/v1/skin-assessment-tasks/{taskId}/photo-versions/{photoVersion}` 仅在任务为 `needs_retake` 时使用。路径 `photoVersion` 必须等于当前版本加一。multipart 中：

- `metadata: application/json`，schema 为 `A02Metadata`。
- `A02Metadata.expectedPhotoVersion` 必须等于当前版本。
- `A02Metadata.replacedViews` 是非空、去重数组，元素只能是 `front|left|right`。
- 实际图片 part 集合必须与 `replacedViews` 完全相等；未替换视角由后端沿用。

任务已被新任务替换返回 `409 TASK_REPLACED`；状态或版本不符返回 `409 PHOTO_VERSION_CONFLICT`。客户端先重新读取任务，再决定是否创建新的逻辑请求。

### 4.5 任务、报告和媒体响应

`AssessmentTaskView`：

- 必填 `taskId`、`status`、`photoVersion`、`requiredViews`。
- `status` 只取 `queued|analyzing|needs_retake|report_ready|failed`。
- `requiredViews` 元素只取 `front|left|right`，仅 `needs_retake` 时应非空。
- 可空 `failureCode`、`retryable`、`reportId`、`planAvailability`。公开 `failureCode` 当前白名单为 `QUALITY_REJECTED`、`NOT_SAME_PERSON`、`IDENTITY_UNCERTAIN`、`IDENTITY_ENROLLMENT_TIMEOUT`、`SOURCE_IMAGE_UNAVAILABLE`、`RESULT_ARCHIVE_FAILED`、`PROVIDER_CONTRACT_VIOLATION`、`MEMBER_NOT_VISIBLE`、`DEPENDENCY_UNAVAILABLE`。

`GimbalCurrentAssessmentView` 包含 `currentAssessment` 和 `currentAssessmentRevision`。没有当前任务时 `currentAssessment` 必须显式为 `null`；有值时为 `{taskId,status,photoVersion,reportId?}`。

`SkinReportView` 必填 `reportId`、`view`，可含 `memberId`、`reportReadyAt`、`conclusion`、`metrics[]`、`description`、`images[]`、`planStatus`。云台只能读取当前任务报告的 `brief`；`brief` 省略 `memberId/metrics/description`。每个 `SkinReportImage` 只有 `mediaId` 和同源受控 `contentUrl`。

媒体读取返回原始二进制，没有 `{requestId,data,meta}`。实际 Content-Type 可为 `image/jpeg`、`image/png` 或 `application/octet-stream`，并带 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`X-Request-Id`。当前 OpenAPI 仅声明整对象 `200`，没有 Range 合同。不存在、不可见、非 available 和授权失败统一 `404 RESOURCE_NOT_VISIBLE`。

## 5. K7 音频线格式

K7 到语音服务的归一化音频格式冻结为：

| 项目 | 值 |
|---|---|
| sample format | signed PCM16LE |
| sample rate | 16000 Hz |
| channels | 1（mono） |
| frame size | 2 bytes |
| byte rate | 32000 bytes/s |

板内采集、VAD/分段、ASR 输入和 TTS 解码后的播放缓冲都以此作为交换格式。任何来自 codec 的 S32/stereo 数据必须先有界转换；不能让不同调用方猜测采样率、声道或端序。

通过 HTTP 上传音频文件时允许包装为标准 PCM WAV：`RIFF/WAVE`、format code 1、channels 1、sample rate 16000、byte rate 32000、block align 2、bits per sample 16；`data` chunk 长度必须等于 PCM 载荷长度，RIFF size 必须与完整 WAV 文件长度一致，Content-Type 使用 `audio/wav`。若直接调用现有 `mimo_v25_profile`，WAV 文件会被 Base64 放入其 JSON Chat Completions 请求；这与下节建议给自有后端增加的 multipart 文件上传端点是两种传输合同。

## 6. 当前 OpenAPI 没有 ASR/TTS

对 `paths` 和 `components.schemas` 做不区分大小写的 `asr|tts|speech|audio|transcri|synth` 检索均为零结果。当前后端不能接收 K7 录音做 ASR，也不能返回可播放 TTS。`GET /api/v1/media/{mediaId}/content` 是受控图片读取端点，不是语音上传或生成接口，不能复用它伪装语音能力。

后端至少需要补充以下合同，路径名称可由后端团队冻结；本文先给出可实现的字段和语义。

### 6.1 建议 ASR 端点

建议 `POST /api/v1/gimbals/{gimbalId}/speech/transcriptions`，仅同一云台 device Bearer，必需 Idempotency-Key，使用 multipart：

- `metadata: application/json`：`schemaVersion: 1`、`audioFormat: "wav"`、`sampleFormat: "pcm_s16le"`、`sampleRateHz: 16000`、`channels: 1`、`language: "zh-CN"`、`capturedAt`、`durationMs`。
- `audio: binary`：Content-Type `audio/wav`；声明单文件字节上限、最大时长和请求总上限。
- 成功 `data`：`transcriptionId`、`text`、`language`、`durationMs`、`model`、可空 `confidence`。`text` 必须有 UTF-8 字节上限。

必须冻结超时、限流、最大时长以及 `UNSUPPORTED_AUDIO_FORMAT`、`AUDIO_TOO_LARGE`、`AUDIO_DURATION_EXCEEDED`、`SPEECH_UPSTREAM_TIMEOUT`、`SPEECH_UPSTREAM_UNAVAILABLE` 等错误的 HTTP 映射和 `retryable`。上游失败不能返回空文本的假成功。

### 6.2 建议 TTS 端点

建议 `POST /api/v1/gimbals/{gimbalId}/speech/syntheses`，仅同一云台 device Bearer，必需 Idempotency-Key，JSON 请求：

- `schemaVersion: 1`
- `text: string`，冻结 UTF-8 字节和字符上限
- `language: "zh-CN"`
- `voice: string`，由后端白名单约束
- `audioFormat: "wav"`
- `sampleFormat: "pcm_s16le"`
- `sampleRateHz: 16000`
- `channels: 1`

第一版可直接返回 `audio/wav` 二进制，并用响应头提供 `X-Request-Id`、`X-Audio-Sample-Rate: 16000`、`X-Audio-Channels: 1`；也可以保持统一 JSON 信封，返回短效 `mediaId/contentUrl` 及 `contentType`、`bytes`、`sha256`、`durationMs`。两种形态必须二选一并写入 OpenAPI，不能让 K7 运行时猜测。上游失败不能返回静音文件的假成功。

### 6.3 后端配置和凭据边界

后端还需冻结：

- 生产 `https://hostname[:port]`、证书链和环境切换规则；当前 `http://10.3.3.170:18085` 不能用于 TLS 验收。
- MiMo 的服务端 endpoint、区域、模型 entitlement 和超时策略。
- MiMo secret 的服务端安全注入和轮换方式。K7 只携带短期 gimbal device session token，不保存上游 API key。
- 请求关联：将本服务 `X-Request-Id` 与上游 request ID 关联，但日志只保留非敏感 ID、状态码、耗时和长度，禁止记录 Authorization、原始音频、ASR 文本、TTS 文本或设备 credential。

## 7. 最小实现与验收门槛

按以下顺序推进，前一门禁未通过时不宣称后一层完成：

1. **IP 门禁**：Wi-Fi 已关联，K7 取得 IPv4、网关和 DNS server；链路断开能取消在途请求。
2. **DNS 门禁**：对后端正式 hostname 连续解析成功；无固定 IP 回退；断网/超时/取消均有界退出。
3. **HTTPS 门禁**：可信时间、熵源、CA、SNI、hostname 和证书链校验通过，verification flags 为 0；证书或 hostname 错误必须失败，禁止 HTTP 降级。
4. **设备会话门禁**：真实 `POST /api/v1/gimbal-sessions` 返回四个必填字段；后续请求只用返回的 device token；日志无 credential/proof/token。
5. **心跳门禁**：严格递增 seq 的心跳 `accepted=true`；重复 seq `accepted=false` 且不推进 revision；旧 token 返回 `SESSION_INVALID` 后能重新握手。
6. **测肤门禁**：三张受支持图片首次返回 `202 queued`；同键同内容返回 `200 replayed=true` 且 taskId 不变；同键异内容得到 409。轮询只能经过合法状态转换。
7. **补拍门禁**：仅 `needs_retake` 且下一 photoVersion 可受理；图片 part 集合精确匹配 replacedViews；旧任务和错版本分别得到明确 409。
8. **报告与媒体门禁**：云台只能读当前任务 brief；APP/full 权限独立验证；媒体逐次授权，失去权限后同一 URL 返回统一 404，并保留 no-store/nosniff。
9. **ASR 门禁（待后端补接口）**：上传 PCM16LE/16 kHz/mono WAV，成功返回有界 UTF-8 文本；格式、时长、超时和上游失败均按冻结错误合同返回，不伪报成功。
10. **TTS 门禁（待后端补接口）**：文本生成 WAV，经头部和 data 长度校验后转换/直接播放；返回非 16 kHz mono 时由明确适配层转换或拒绝；上游失败不播放成功提示。
11. **整机闭环**：语音意图只能提出动作。K7 实际完成拍照、上传、任务受理或设备控制并拿到真实结果后，才允许 TTS 播报“完成”；模型文本本身不能作为设备动作成功证据。

当前可并行完成 DNS/HTTPS 板端门禁和后端 speech OpenAPI 设计；当前抓取的后端接口只能验收云台/测肤/媒体链，不能验收 ASR/TTS。
