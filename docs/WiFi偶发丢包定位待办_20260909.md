本记录来自已完成的 `evidence/stability-20260909/coexist-run-01/`，完整结果为 1497/1500；本记录用于定位，未修改固件。

## 已知事实

| 周期 | Ping | 未收到的序号（从 0 开始） | BLE | RX 拒绝计数 |
|---|---|---|---|---|
| 12 | 50 发 / 49 收 | 0 | 连接、加密保持；无新增断开 | 26 → 26 |
| 16 | 50 发 / 48 收 | 8、28 | 连接、加密保持；无新增断开 | 27 → 27 |

这些周期 Wi-Fi 仍在线，IP 不变，网络队列 dropped 为 0，空闲堆未变。第 12 周期 A-MSDU 完整组 3 → 4、子帧 6 → 9；第 16 周期这些计数不变。计数只能提供定位线索，不能证明因果。

已只读检查当前 Ubuntu SDK 的 `apps/netutils/ping/icmp_ping.c`：Ping 序号从 0 开始，单次超时后继续下一序号。保存的正常周期含 0..49，第 12 周期缺 0，因此不能误写成“最后一包提前结束未统计”。`CONFIG_NET_ARP_SEND=y`，ICMP 发送路径包含邻居解析；现有证据尚不能证明 ARP 是原因。

## 下一版诊断应增加什么

1. 主机采集保留 Ping 的 `No response`、迟到序号、ID 不符等安全元数据。当前白名单保留成功回复及最终统计，未完整保存这些诊断行。
2. 分层记录 ICMP 发送序号、发送命令返回值、接收序号及网络栈交付结果；只留头部标识与计数，不采集密码、密钥或完整业务载荷。
3. 区分无线接口收到但丢弃、交给网络栈后拒绝、没有收到对应回复、回复超过超时窗口。不能用一个总 RX 计数替代分层证据。
4. 固定同一版本、网络和采样条件做针对性复测。必要时增加参考网络测量，但先核对是否同一路径，不能把 PC/Linux 参考结果当原生驱动验收。

本轮零丢包标准保持不变。连接保持、零丢包、应用端到端通信分别验收。不要为了得到通过结果而删除重放保护、吞掉错误、重启设备清空计数，或把超时包改写成成功。

正式结果以本轮 `result.json` 与 `测试结果.md` 为准。以上是已观测到的两个周期，若后续新增丢包，需据完整记录更新。
