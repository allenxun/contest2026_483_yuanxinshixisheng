实板支持 fastboot usb；控制器 0 无主机枚举，控制器 1 报 high-speed，并枚举为 18d1:4d00、USB download gadget。Windows 错误码 28，用户将设备连接到 Ubuntu 后 Linux 枚举成功。PyUSB 1.3.1 仅安装于 /dev/shm/velavision-usb-pydeps-20260911。

256 字节已知数据下载 ACK 成功；串口 Ctrl+C 返回 U-Boot，0x40c00800 CRC32=29058c73，与源一致，前16字节读回00..0f。传输工具计时约0.0063秒，仅代表小数据，不代表完整镜像性能。原始记录 small-download.json、small-crc.log、small-data.log。

目标：OTG 传输镜像，串口控制及日志，不刷 eMMC。尚未完成真机 USB 传输。

已从已下载官方 SDK 的 Git 对象库提取并核对 fastboot.c、f_fastboot.c 和 rk3576_defconfig；输入提交及 SHA256 见 evidence/usb-fastboot-preflight-20260911/audit.json。

该 SDK 的命令为 `fastboot usb <controller>`。默认缓冲区为 0x40c00800，长度 0x07000000。download 回调仅复制到缓冲区；flash 是独立回调。命令循环接受串口 Ctrl+C 后退出。以上是源码事实，不证明现有板载 U-Boot 必然使用该配置。

tools/fastboot_ram_download.py 仅实现 download 协议，不实现 flash、erase、boot、continue、reboot 或 OEM 命令。要求精确 VID/PID/USB 序列号、Fastboot 接口、镜像 SHA256 和已审计的运行缓冲区。USB ACK 不代表 RAM CRC 或启动成功。tools/test_fastboot_ram_download.py 的 6 项主机协议测试通过；尚无 USB 实测吞吐率。

下一步：恢复串口枚举 → 核对现有 U-Boot help、内存布局与下载缓冲区 → 进入 Fastboot 并核对 USB 身份 → 小数据 RAM 下载 → Ctrl+C 返回并读回/CRC → 完整镜像下载校验及 RAM 启动。镜像目标 0x40400000 与默认下载缓冲区存在潜在重叠，必须审查实际复制方式；多文件装载必须避免后续下载破坏已搬移镜像，不能直接循环覆盖缓冲区。

当前电脑起初识别到 COM8，之后用户拔插串口，Windows 与 Ubuntu 后续枚举均未见串口或 Rockchip 下载设备。串口打开返回设备不存在，没有发送重启或下载模式命令。用户已确认 OTG 数据线接好。需恢复可见的串口后继续设备步骤。

优先目标仍是离线规则语音配网；DNS/HTTPS 延后。当前语音 trace 镜像已 RAM 启动，Add 探针在 Session 创建阶段未返回；此前控制台仍可读取状态，本轮失去串口枚举不能据此判断固件崩溃。


## 用户确认的后续传输约定

后续固件镜像统一优先通过 OTG Fastboot RAM 下载，串口仅用于控制、CRC校验、启动和日志。不得因枚举问题静默回退到逐条 mw.q 的大镜像串口传输；先恢复 OTG 或说明实际阻塞。该约定不授权刷写 eMMC，也不免除镜像哈希、内存范围和完整 CRC 校验。当前已验证控制器1、18d1:4d00；重复枚举若受 VMware 接管影响，按已记录方法恢复。

## 2026-09-12 VMware 启动卡死与恢复

本轮确认 VMX 中的 `usb.autoConnect.device0 = "vid:18d1 pid:4d00 autoclean:0"` 会在 Ubuntu 开机阶段触发 Windows 停止 OTG 设备；USB 仲裁未完成时，`vmware-vmx` CPU 增量为 0、VMware Tools 无 IP、SSH/Ping 均不可达。结束唯一无响应的 VM 进程、备份 VMX 并移除这条开机自动接管规则后，Ubuntu、Tools、NAT 和 SSH 正常恢复。虚拟机仍为 8 vCPU、16 GiB，主机有约 32 GiB 内存；本次卡死不是来宾磁盘或内存不足。

虚拟机启动后通过 `vmrun writeVariable ... runtimeConfig usb.autoConnect.device0 "vid:18d1 pid:4d00 autoclean:0"` 写入运行时规则成功；板端由 Windows CH340 COM11 执行 Ctrl+C 和 `fastboot usb 1` 后确实重新枚举。随后 VMware USB 代理进入 Code 43，设备未出现在 Ubuntu `lsusb`，当前自动权限不能重启 `VMUSBArbService` 或重新初始化代理。板子已退出 Fastboot并留在 U-Boot `=>`，不会静默回退到串口传大镜像。恢复方式为管理员 PowerShell 重启 `VMUSBArbService` 或物理重插 OTG，再在 Ubuntu 完全启动后接管设备。证据见 `evidence/voice-rule-wakepartial-20260912/acceptance.json`。
