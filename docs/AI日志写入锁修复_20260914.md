# AI 日志写入锁修复与交接

本轮只修改工具和隔离测试，没有导出真实日志、改动 `logs/`、启停 watcher 或执行硬件操作。日志原始数量仍以实时 manifest 为准，不能从本次测试推导新快照事件数。

## 发现与复现

原有 `watcher.lock` 用于防重复监测进程，`writer.lock` 用于协调 Stop hook、监测器与手动导出。手动 CLI 导出和 `collect()` 内部官方校验已经持有写锁，不应把所有数量变化归因于缺少写锁。

隔离双进程回归确认一个实际问题：`writer_lock()` 在调用 `msvcrt.locking` 前读取锁文件第一个字节。Windows 字节范围锁阻止另一个进程读这个字节，因此竞争进程直接在 `read(1)` 抛 `PermissionError`，还没有进入等待锁的逻辑。修复前并发回归失败，修复后通过。该问题会造成采集/导出争用时异常退出，并非已证明能直接绕过锁造成并发写坏文件。

另一个可复现设计窗口是：分日 JSONL 逐文件替换后才更新 manifest。独立直接运行原版 `validate-log.py` 不持项目锁，有可能读取两个版本混合的快照。锁只协调采用相同入口的读写者，不保护外部编辑程序或其他不持锁脚本。

## 修改

- `auto_collect_logs.writer_lock()` 先取得 Windows 范围锁，再初始化空锁文件；不在获取锁前读取被锁字节。
- `watch_project_logs.py` 的单实例锁同样先锁再初始化，第二个监测器由非阻塞加锁结果正常退出。
- `export_project_logs.main()` 内部统一进入写锁，直接 Python 调用也获得与 CLI 相同保护。
- 新增 `tools/validate_project_logs.py`：持有同一写锁运行**未修改的原版**官方校验器，保留退出码与输出。
- `test_log_writer_coordination.py` 使用临时目录和真实子进程验证互斥，以及程序调用、错误释放和校验退出码；不访问真实日志。

## 验证与下一模型操作

从 `tools/` 执行：

```text
python -X utf8 -m unittest test_log_writer_coordination test_log_export_core test_auto_collect_logs test_log_daily -v
```

13 项通过，其中真实 Windows 并发测试修复前失败、修复后通过。该结果仅是工具回归；不等于重新运行官方日志校验。证据：`evidence/log-writer-lock-20260914/verification.json`。

后续由负责主会话的代理统一核对监测器命令行、重启已授权的现存监测器以加载新代码，再手动导出显式项目会话。常驻 Python 进程不会自动加载本次改动。本子任务没有启停任何真实监测器。

实时日志校验推荐使用：

```text
python -X utf8 tools/validate_project_logs.py
```

导出 `tools/export_project_logs.py` 已在写锁内调用原版校验，并更新交付证据。不应从多个代理同时触发导出。`LK_LOCK` 沿用 Windows 有限重试语义，超时失败应待前一操作结束后重试，不能删除锁或绕过锁。锁不提供多文件崩溃事务；进程被强杀后仍需重新导出和校验。

项目主线现为 BLE 选择 Wi-Fi、手动输入密码、板端 DHCP 成功回报与提示、再进入云 ASR/TTS。AI 日志应记录这一真实变化和旧 heartbeat 误启动的修正，不继续把离线语音口述密码作为当前验收目标。
