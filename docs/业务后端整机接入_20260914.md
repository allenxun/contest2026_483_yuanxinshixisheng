# K7 整机对接业务后端

以用户最新确认为准：业务后端地址为 `http://10.3.3.170:18085`。K7 对接后端，由后端负责知识库、模型及业务编排。3000 工作流页面不作为 K7 直接调用接口。

## 当前已核实的调用顺序

1. App BLE 发送 X 获取 Wi-Fi 列表，再发送 connect 和凭据；K7 成功获得 IP 后给 App 回报 wifi_connected。
2. K7 以 credential、credentialVersion、proof 调用 `POST /api/v1/gimbal-sessions`。该请求不带 Bearer，不自行声明 gimbalId。
3. 从响应 data 读取 gimbalId、sessionToken、expiresAt、serverTime。
4. 带设备 Bearer 调用 `POST /api/v1/gimbals/{gimbalId}/heartbeats`，提交 observationEpoch、observationSeq、observedAt、powerState。只有后端接受真实心跳后，才能宣称后端已确认在线；BLE 的联网成功不等于后端设备认证成功。
5. ASR 的完整句子交给后端对话接口，由后端返回回答，再交给 TTS 播放。此接口尚未在当前 Swagger 中找到，需要后端提供合同。

设备凭据与云模型 API Key 是不同凭据，不能混用。不能虚构 proof 或复用其他设备身份。现有 `frontend/gimbal-cloud-client.mjs` 已实现设备会话、心跳和状态接口，本轮7项模拟回归通过；尚未使用真实设备凭据认证。

## 后端联调需要提供

- 当前 K7 的设备凭据配置位置或生成步骤：credential、credentialVersion、proof。Swagger 明确 proof 由凭据提供方定义，其具体格式尚未冻结。
- 后端聊天入口：方法/路径、请求体、鉴权、会话ID、回答格式；如果支持流式，给出事件及结束/错误标志。

这些信息齐备后，先做设备认证与一次真实心跳，再接 ASR 文本→后端回答→TTS。厂商密钥留在服务端，语音测试不自动触发护理、云台或其他设备动作。
