# K7 原生驱动移植与证据归档

目标是把一个明确的外设能力从源码假设推进到可复核的真机结果。先读取项目最新接续说明和现场日志，识别当前板态、已验证能力及未完成边界，不沿用更早的启动提示覆盖最新状态。

## 原厂对照与定位

1. 从实板 ID、器件标签、运行日志确认装配；原理图的兼容器件名、设备树占位字符串和芯片规格不能覆盖实测身份。
2. 优先使用用户本地官方 SDK。记录压缩包校验值、SDK 基线、实际驱动路径、固件哈希和引用的代码位置。Linux `.ko` 不是 openvela 可加载驱动。
3. 对照正常系统的初始化顺序、时钟、供电、复位、引脚复用/上下拉和总线交互。读取“启动失败后”的状态不能倒推启动前状态。只保留能区分假设的下一项实验，不重复相同失败来累计测试数量。
4. 原厂与原生结果不同时，尽可能固定内核、DTB、RAM shell 和供电条件，仅改变一项。用结果收窄因果；不要由寄存器读回推定实际电压，也不要由引脚相关性臆测未公开的 strap 定义。

## 原生实现

按总线枚举 → 数据事务 → 固件下载/读回 → 固件就绪 → 协议/系统接口 → 扫描/连接推进。每一层使用前一层的实测结果作为前提。

- 从厂商源码提取协议事实，重写 Linux 锁、线程、内存、IRQ、网络/HCI 接口为当前 NuttX 对应接口；保留来源和许可。
- 将硬件边界、传输协议和系统桥接分开。明确缓冲区生命周期、长度、尾字节、超时、错误状态以及调用方持锁约定。
- 遇到部分写入或超时即保留失败现场，不盲目重试固件写入并继续启动。测试覆盖短包、块边界、错误完成顺序和异常收尾。
- 先核对当前 NuttX API 的成功返回值和接收回调规则；“编译通过”只计为编译证据。

## RAM 验证

使用项目已有、已校验的加载工具及独立镜像名，保留旧镜像。编译前后核对配置和已验收镜像的哈希；无需重复既有应用验收。

在写入 RAM 前，结合真实 DTB 内存 bank、reserved-memory、固件/OP-TEE 保留区、U-Boot 重定位、内核段和堆范围核对所有区间。一个地址属于物理 DDR 并不意味着可供普通系统使用。暂存区若在堆外，必须有正确且最小权限的 MMU 映射。

镜像和固件分别检查可信输入哈希、文件长度及完整 RAM CRC；固件下载后按实验目的读回核对。收到真实就绪消息才能计为固件启动，收到 HCI 回应不能计为蓝牙配对，Wi-Fi 扫描不能计为联网。

串口一次只允许一个进程占用；根据现场记录使用正确端口/波特率和调制解调器信号状态。等待上一进程退出后再开始下一操作。遵守当前会话已授权的启动范围，不以 RAM 实验的名义默认授权磁盘挂载、刷写或执行器动作。

## 输出规范

交付以下实际产物，不填造假占位数据：

- 源码/补丁与来源许可；独立构建目录、配置、源码和镜像 SHA256。
- 原始构建日志、串口命令/输出、检查结果及复现入口。
- 简短的“假设—改动—观测—结论”表；明确哪些为推断。
- 当前板态、串口占用情况、恢复入口和下一项有区分力的实验。
- 分层完成状态：已实现、已编译、已在真机验证、仍未完成。

参赛材料只陈述对应证据支持的能力；AI 开发记录应关联真实修改和工具输出。远程提交须采用用户提供的赛事官方仓库及指定分支，不能用个人仓库替代，也不能把本地分支存在写成已经合入。
