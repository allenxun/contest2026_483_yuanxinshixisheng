本轮按用户明确范围实现：**蓝牙连接 → 真实 Wi-Fi 列表 → 提交选中的 SSID 和密码 → 设备确认收到**。不尝试 Wi-Fi 认证、不启动 DHCP，不要求联网成功。

设备仅在处理当前请求时将信息放在内存中，校验后即擦除，回包明确 `stored:false`；没有持久保存，也不在以后自动联网。此阶段“已收到”是传输/格式验证成功，不表示密码正确。

## 用能力字段决定是否开放输入

读取 Status characteristic：

```json
{"v":1,"scan":true,"receive_credentials":true,"connect":false,"encrypted":true,"busy":false,"session":1,"commands":0}
```

- `receive_credentials:true`：开放密码输入和“发送给设备”按钮，调用 `submitCredentials()`。
- 字段缺失或 false（旧 id36 固件）：仍然禁用发送。**编译产物存在不代表板端已升级，必须读实际能力。**
- `connect:false`：不能调用真正联网；`connectWifi()` 仍返回 `not_ready`。

## 提交格式与规则

使用相同 UUID、加密连接、Notify 订阅、20 字节串行 Write 和 JSONL 末尾 LF：

```json
{"v":1,"id":103,"cmd":"submit_credentials","ssid_b64":"TGFuc2Vl","password":"EXAMPLE_ONLY_123"}
```

示例密码不是实际凭据。`id` 为 1..65535 整数；`ssid_b64` 原样使用扫描列表字段，必须为标准规范 Base64、解码后 1..32 字节。密码限定 **8..63 个可打印 ASCII 字节（0x20..0x7e）**；首尾空格、引号、反斜杠必须保留，不 trim。JSON 转义交给 `JSON.stringify`。本阶段格式校验不判断 AP 认证类型或密码是否能联网。

```js
const receipt = await ble.submitCredentials({
  ssid_b64: selectedAccessPoint.ssid_b64,
  password: passwordInput
});
// 显示：设备已收到，尚未联网。随后清空密码输入框。
```

回包：

```json
{"v":1,"id":103,"session":1,"event":"credentials_received","validated":true,"stored":false,"wifi_connected":false,"ip":null}
```

格式失败：

```json
{"v":1,"id":104,"session":1,"event":"error","code":"invalid_password"}
```

错误码包括 `invalid_ssid`、`invalid_password`、`invalid_command`；无有效 id 的畸形命令不保证沿用请求 id。响应以当前 BLE `session` 与 `id` 关联；客户端等待 15 秒。ATT 写入成功不是业务接收成功，只有收到匹配的 `credentials_received` 才显示成功。断线/超时后提示“未确认收到”，不自动重发密码。
