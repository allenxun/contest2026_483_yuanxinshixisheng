# VelaVision K7 前端蓝牙联调操作手册

当前设备已换为 `phone-rpa-20260909`，修复重新配对时随机地址混用问题；服务已启动，手机重新配对和业务收发复测待完成。之前初次保持连接通过不等于重复配对稳定性通过。UUID 和业务协议保持一致。

日期：2026-09-09。适用：Android / iOS App，包括 uni-app。

手机蓝牙调试器先看 [手机调试器操作卡](手机调试器操作卡.md)，手动提交示例分包见 `手机调试HEX分包.txt`。前端 App 使用本手册及 `.mjs` 适配器。

## 一、本次只做什么

**前端连接板端蓝牙 → 请求 Wi-Fi 列表 → 选择网络并发送密码 → 收到板端“已收到”回执。**

不要求真正连上 Wi-Fi。成功提示写 **“OK，设备已收到”**，不要写“Wi-Fi 已连接”。板端校验信息后即擦除，不保存密码，也不自动尝试联网。

设备名称：**VelaVision K7**。设备端已启动此功能，本机 Windows BLE 客户端已实测成功；Android/iOS App 需要按下面步骤进行联调。

## 二、拿到哪些文件

将以下三个文件放在项目同一目录，保持文件名不变：

| 文件 | 用途 |
| --- | --- |
| `vela-provision.mjs` | BLE 适配器，封装连接、分片、通知组包、扫描和提交 |
| `接入示例.mjs` | 界面回调示例，含 `openVelaWifiList()`、`submitWifiDetails()` |
| `test-vela-provision.mjs` | Node 软件测试，可运行 `node --test test-vela-provision.mjs` |

请使用本次附带版本；旧版没有 `submitCredentials()`。

## 三、连接设备

1. 使用 App 真机运行，取得系统要求的蓝牙权限，打开手机蓝牙。
2. 在 App 中扫描并选择 **VelaVision K7**。`deviceId` 使用当前手机扫描结果，iOS 不要写死 MAC。
3. 停止 App 的设备扫描，再调用 `ble.connect(deviceId)`。
4. 配对/加密如需系统交互，按手机提示完成。仅在系统设置中看到“已配对”不代表业务连接已就绪。

```js
import { VelaProvision } from './vela-provision.mjs';

const ble = new VelaProvision(uni, {
  onConnection: ready => {
    // 更新蓝牙状态；ready=false 时禁用提交。
  },
  onAccessPoint: ap => {
    // 可逐条显示扫描结果；保留 ap.ssid_b64 原始值。
  }
});

// deviceId 来自本 App 的蓝牙设备扫描页面。
const capabilities = await ble.connect(deviceId);
```

适配器会完成服务发现、订阅 Notify 和读取加密状态。连接返回后核对：

```json
{"v":1,"scan":true,"receive_credentials":true,"connect":false,"encrypted":true,"busy":false,"session":25,"commands":0}
```

`session` 和 `commands` 是动态值。**是否开放密码发送看 `receive_credentials:true`，不要用 `connect:false` 禁掉本轮的信息发送。** `connect:false` 只表示真正联网尚未开放。如果没有 `receive_credentials` 或它为 false，联系设备同事确认固件版本。

## 四、请求并展示 Wi-Fi 列表

```js
const result = await ble.scan();
const networks = result.networks;
```

适配器发送单字节 ASCII **`X`**（0x58，不带换行）。**当前不是连接后自动推送，前端需要主动调用一次 `scan()`。**

板端依次返回 JSONL 消息，以下仅为格式示例：

```json
{"v":1,"id":1,"event":"scan_started"}
{"v":1,"id":1,"event":"ap","ssid_b64":"TGFuc2Vl","rssi":-45,"security":"rsn","band":"2.4G","channel":1}
{"v":1,"id":1,"event":"scan_done","count":1,"truncated":false}
```

- `ssid_b64` 是 SSID 原始字节的 Base64；示例 `TGFuc2Vl` 对应 Lansee。
- 展示名称可解码，但提交时必须保留原始 `ssid_b64`，不要重新编码显示名。
- `count` 表示原始 AP 行数，同一网络名称可能出现多条；适配器先核对行数，页面再按需要合并展示。
- `truncated:true` 表示结果达到容量上限，可提示“显示部分结果”。
- 扫描等待上限为 60 秒，收到 `scan_done` 才算本次列表接收完成。

## 五、选择网络并发送密码

界面按钮建议写 **“发送给设备”**。先用测试密码验证消息通道，不必使用真实 Wi-Fi 密码。

```js
const receipt = await ble.submitCredentials({
  ssid_b64: selectedAccessPoint.ssid_b64,
  password: passwordInput
});

// Promise 成功返回才显示：OK，设备已收到。
// 清空密码输入框，不写控制台、埋点或本地存储。
```

输入规则：

- SSID：规范 Base64，解码后 1..32 字节。
- 密码：8..63 个可打印 ASCII 字节（0x20..0x7e）。可用测试值 `EXAMPLE_ONLY_123`。
- 保留密码首尾空格、引号和反斜杠，不 `trim()`，不自动添加字符。
- JSON 转义由适配器的 `JSON.stringify` 处理，不手工拼接字符串。

实际发送格式（末尾追加 LF，即 `\n`）：

```json
{"v":1,"id":103,"cmd":"submit_credentials","ssid_b64":"TGFuc2Vl","password":"EXAMPLE_ONLY_123"}
```

板端成功回执：

```json
{"v":1,"id":103,"session":25,"event":"credentials_received","validated":true,"stored":false,"wifi_connected":false,"ip":null}
```

`credentials_received` 就是本轮的 **OK / 已收到**。它不是裸字符串 `OK`，不表示密码正确，也不表示联网。`stored:false` 表示设备未保存这份信息。

适配器按本次 `id` 和当前 `session` 匹配回包，等待上限 15 秒。不要调用 `connectWifi()` 或发送 `cmd:"connect"`，这两个入口仍返回 `not_ready`。

## 六、如果自己实现 BLE 通道

使用以下固定 UUID：

| 项目 | UUID | 操作 |
| --- | --- | --- |
| Service | `6b7a0001-78c3-4f2e-9c2f-3ecbc2d74680` | 发现服务 |
| Write | `6b7a0002-78c3-4f2e-9c2f-3ecbc2d74680` | 前端写给板端 |
| Notify | `6b7a0003-78c3-4f2e-9c2f-3ecbc2d74680` | 订阅板端回复 |
| Status | `6b7a0004-78c3-4f2e-9c2f-3ecbc2d74680` | 读取能力 |

先订阅 Notify、确认加密就绪，再发命令。Write 使用带响应写入，每片最多 **20 字节**，串行等待写完成；每条 JSON 使用 UTF-8 编码并追加 LF，总长最多 512 字节，首片到达后应在 **10 秒内**发完。适配器自动分包。Notify 可能拆成多片或连续多条，先拼字节，按 LF 分行，再解析 JSON。

JSON 命令 `id` 为 1..65535 的整数，同一时间只发一个业务事务。BLE 写入成功只表示传输已接受；必须收到业务回包才算完成。普通聊天文字不是该协议。

## 七、失败时如何处理

2026-09-09 配对修正版 `phone-pairing-20260909` 已从 RAM 启动并确认服务广播；手机重新配对及加密连接至少 100 秒已通过，长时间稳定性、重连和本轮手机业务收发仍待验证。它保留最多 8 台设备配对记录，满时轮换清除未连接设备的旧记录，允许新设备配对。被清除的客户端下次需要重新配对；当前同时只服务一台前端，断开后其他手机可以接入。RAM 重启不保留这些配对密钥，手机若使用旧记录失败，应忽略旧配对后从 App 重新配对。

配对失败时先检查配对/加密过程，不要通过修改 UTF-8、换行符或重复发送 X 来尝试维持连接。系统“已配对”和 App 短暂“已连接”均不能代替加密、Notify 订阅和业务回包验证。

| 现象 / 错误码 | 处理 |
| --- | --- |
| 找不到设备 | 确认板子供电和服务已启动；本版本是 RAM 启动，重启后需设备同事确认 |
| 已配对但 App 连不上 | 确认无其他客户端占用；若板端重启过，可取消旧 VelaVision K7 配对后在 App 重连 |
| `not_ready` | 核对接收能力及是否误用了 `connectWifi()` |
| `invalid_ssid` | 原样提交扫描返回的 `ssid_b64`，不能提交显示名 |
| `invalid_password` | 检查长度、字符范围；此错误不是“路由器密码错误” |
| `invalid_command` | 检查 JSON、v、id、cmd 和末尾 LF |
| 写入失败 / busy | 确认加密及 Notify 订阅，等当前事务完成再发下一条 |
| 超时 / 蓝牙断开 | 显示“未确认收到”；不自动重放密码，重连后由用户重新提交 |

页面退出时调用 `await ble.dispose()` 释放连接。不要为了测试改动上述 UUID 或把接收成功映射为联网成功。
