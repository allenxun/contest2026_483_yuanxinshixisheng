## 2. 前端现在可以做什么

业务顺序：App 扫描 K7 → 建立 BLE 连接 → 发现服务 → 订阅通知 → 确认链路加密 → 发 `X` → 接收 Wi-Fi 列表。

列表和状态走 **BLE**，不依赖 K7 已连接 Wi-Fi。Wi-Fi 扫描与 BLE 消息收发的共存已测试；“Wi-Fi 已联网并持续传输数据时的蓝牙共存”仍需下一阶段测试。

界面建议分别显示：`蓝牙未连接`、`正在连接`、`蓝牙已就绪`、`正在扫描`、`扫描完成`。只有 `connect:true` 的后续版本才开放密码提交，只有真实 `wifi_connected:true` 且有 IP 才可显示已获取网络地址。获取 IP 与互联网可达也应分别判断。

## 3. BLE 设备与 GATT UUID

设备名：**VelaVision K7**。广播包含服务 UUID，名字可能稍后在扫描响应包中出现，不能因第一包名称为空就丢弃设备。

| 用途 | UUID | 属性 / 要求 |
|---|---|---|
| 配网服务 | `6b7a0001-78c3-4f2e-9c2f-3ecbc2d74680` | Primary Service |
| App 写命令 | `6b7a0002-78c3-4f2e-9c2f-3ecbc2d74680` | Write With Response；链路已加密、已订阅通知 |
| 板端回消息 | `6b7a0003-78c3-4f2e-9c2f-3ecbc2d74680` | Notify；每次连接重新启用 CCCD |
| 读取能力和状态 | `6b7a0004-78c3-4f2e-9c2f-3ecbc2d74680` | Read；可在加密完成前读能力 |

UUID 已由真实客户端发现并收发验证，并非待实现的拟定值。**前端按 UUID 发现，不硬编码 ATT handle 或固定 MAC 地址。** iOS 的 `deviceId` 应使用当前 App 扫描得到的设备标识。

板端会请求加密，系统可能弹出配对提示；完成配对后仍需做服务发现、通知订阅和业务收发。当前采用 Just Works 加密配对，不宣称具备 MITM 身份验证。绑定密钥目前仅保存在 RAM；重启/断电后若出现旧绑定导致的连接失败，需要在客户端移除该 K7 的旧绑定再配对。正常断开重连不应反复取消配对。

当前服务面向一个前端连接。开发电脑测试连接未释放时，手机不应同时占用同一板端服务。

## 4. 字节协议与分包

| 项目 | v1 规则 |
|---|---|
| 字符编码 | UTF-8；完整消息拼好后再解码，不能逐个 BLE 包独立解码中文 |
| 普通消息边界 | 一条 JSON 对象，以 LF `0x0A` 结束；JSON 字符串内换行使用转义 |
| 快捷扫描 | **独立写入一个字节** ASCII `X`，即 `0x58`，不追加换行 |
| App 每次写入 | 1–20 字节，Write With Response，逐包等待写成功再写下一包 |
| 板端每次通知 | 最多 20 字节；多个通知拼成一条 JSONL；不能假设一通知等于一消息 |
| 单条命令 | 最多 512 字节，含末尾 LF；同一 BLE 写包不能包含多条命令 |
| 半包超时 | 从首片开始 10 秒；超时清除缓存，App 应放弃本次请求并重新开始 |
| 并发事务 | 一次只发一个命令，收到完整终止事件再发下一条；扫描期间不得交叉发送状态或联网命令 |
| 事务编号 | JSON 请求 `id` 为 1–65535 整数；前端生成；`X` 的 id 由板端生成，从 `scan_started` 获取 |
| 超长输入 | 拒绝并丢弃；不要继续补发原命令。重连可重置输入状态，禁止自动重放密码 |

蓝牙 MTU 可协商，当前 Windows 真机请求 527，板端协商到 247。**应用层仍固定 20 字节分片**，前端不必申请大 MTU；这让默认 MTU 下也能使用同一协议。

写成功只表示当前分片被接受，业务完成以相应 JSON 事件为准。通知模式没有本协议额外的逐片应用 ACK，前端必须检查终止事件、事务 id 和列表数量；超时或数量不符即视为本次事务失败，不能显示不完整列表为成功。

## 5. 读取能力

读取 Status 特征的响应示例（字段值随会话变化）：

```json
{"v":1,"scan":true,"connect":false,"encrypted":true,"busy":false,"session":31,"commands":116}
```

- `v`：协议版本，当前为 1；未知版本停止发送业务命令。
- `scan` / `connect`：分别表示扫描、真正连接 Wi-Fi 的能力。本版固定为 true / false。
- `encrypted`：当前 BLE 链路加密状态，true 后再发业务命令。
- `busy`：板端正在处理一个事务；等待完成，勿并发写入。
- `session`：当前运行期间的会话代数，断线或取消通知会改变；不应持久保存为设备身份。
- `commands`：本次启动后已接收完整命令的累计数，用于联调诊断。

uni-app 的读取数据通过 `onBLECharacteristicValueChange` 返回。示例适配器区分 Status 读取回调和 Notify 业务消息，并等待真实加密状态才让 `connect()` 成功返回。

## 6. Wi-Fi 扫描

发送单字节 `X`；或发送下面的 JSON 并追加 LF：

```json
{"v":1,"id":101,"cmd":"scan"}
```

板端按序回传以下消息。这里的 RSSI、信道、数量仅为字段示例，不是测试原始记录：

```json
{"v":1,"id":101,"event":"scan_started"}
{"v":1,"id":101,"event":"ap","ssid_b64":"TGFuc2Vl","rssi":-45,"security":"rsn","band":"2.4G","channel":1}
{"v":1,"id":101,"event":"scan_done","count":1,"truncated":false}
```

| 字段 | 说明 |
|---|---|
| `ssid_b64` | SSID 原始字节的 Base64，解码后最多 32 字节；连接标识应保留此值，不对显示文本重新编码 |
| `rssi` | 信号强度 dBm，通常越接近 0 越强 |
| `security` | `rsn`、`wpa`、`protected`、`open`；`rsn` 仅表示发现 RSN 信息，不能一概等同于 WPA2-PSK |
| `band` | `2.4G` 或 `5G` |
| `channel` | 扫描报告信道号 |
| `count` | 本事务发送的 `ap` 行数；必须与客户端收到的行数一致 |
| `truncated` | 内部最多保留 64 条 BSSID 记录；超出会返回 true，可提示“结果较多，已显示部分” |

同一 SSID 的不同 AP/BSSID 可产生多行，当前协议没有输出 BSSID 字段。因此 `count` 不是唯一 SSID 数量，不能先去重再拿去重后的数量与 `count` 对比。先验证原始接收行数，再按 SSID 原始字节、频段和安全信息整理展示。

空 `ssid_b64` 表示没有可展示的 SSID，可显示“隐藏网络”。非 UTF-8 SSID 应保留原始 Base64，使用明确的备用显示文本；不要默默丢字节、替换字节后用于连接。

扫描失败时返回：

```json
{"v":1,"id":101,"event":"error","code":"scan_failed","detail":-110}
```

`detail` 是诊断用的板端错误值，界面显示“扫描失败，请重试”即可，不必将内核细节呈现给产品用户。前端扫描事务超时建议 60 秒。

## 7. 状态查询与尚未开放的联网命令

请求及响应：

```json
{"v":1,"id":102,"cmd":"status"}
{"v":1,"id":102,"event":"status","wifi_connected":false,"ip":null,"session":31}
```

前端状态事务超时建议 15 秒。长测使用约每 5 秒一次状态请求，扫描期间暂停该心跳，扫描结束后恢复。

本版对 `connect` 的真实响应是：

```json
{"v":1,"id":103,"cmd":"connect"}
{"v":1,"id":103,"event":"error","code":"not_ready"}
```

底层诊断已实测 Lansee 关联响应成功（status=0、AID=3），并观察到 EtherType 为 `0x888e` 的接收帧前缀，随后正常清理测试连接。这不等于完成 EAPOL 密钥握手，更不等于取得 IP；因此接口仍然如实保持 `connect:false`。

未来前端输入的 `ssid_b64`、`password` 字段已经预留，但本版不使用它们驱动认证，不能凭它们判断已连接。本次联调和示例不发送真实 Wi-Fi 密码；`connectWifi()` 在客户端直接拒绝并返回 `not_ready`。后续实现 WPA2、密钥安装、netdev 和 DHCP 后，需要发布新的能力说明、连接事件与错误码，并完成真实联网测试，再启用密码输入和提交。

2026-09-09 补充：完整交付文件见 [交付入口](交付入口.md)，密码格式、规则、过程与结果事件仅列在 [待实现契约草案](完整配网待实现契约.md)，不可当作当前接口。本版示例始终禁用密码输入和提交；即便后续固件返回 `connect:true`，也须升级适配器及正式事件协议后才启用。

无法解析、未知版本/命令、重复键、非法 id 等输入会返回 `invalid_command`；解析失败时不能保证沿用非法请求的 id。传输层拒绝（未订阅、未加密、忙碌、错误长度等）可能表现为 ATT/系统写入失败，**不保证另有 JSON `busy` 响应**。

## 8. 断线、重连与失败处理

1. 监听 BLE 连接事件；断开后清空正在拼装的通知、待发送分片与事务等待。页面及时撤销“蓝牙已就绪”。
2. 重新扫描或使用仍有效的设备标识，建立连接后重新发现服务、重新订阅通知并读取加密状态。
3. 示例 `reconnect(deviceId)` 最多尝试 3 次，间隔 1 秒、2 秒；恢复后由页面主动重发查询或扫描，**不会自动重放旧事务或密码**。
4. 扫描中断、半包中断后，旧会话的数据不会发到新会话。不要将新一轮扫描与上次的半份列表拼接。
5. App 后台/锁屏能力、操作系统权限和扫描策略由移动端实现决定，需要用目标手机单独验收。

板端已修正“终止通知送出后 busy 标志尚未释放”的竞态，100 次连续请求已实测通过。前端收到完整终止事件即可发下一命令，无需添加经验性的收尾延迟。

## 9. uni-app 集成文件和最小用法

- `vela-provision.mjs`：UUID、UTF-8 JSONL 组包、20 字节串行写、能力读取、状态与扫描、断线取消、有限重连。
- `接入示例.mjs`：连接、扫描、SSID 显示及界面回调示例。
- `test-vela-provision.mjs`：Node 软件回归测试；不替代 Android/iOS 真机测试。

```javascript
import { VelaProvision } from './vela-provision.mjs';

const ble = new VelaProvision(uni, {
  onConnection: ready => { /* 更新蓝牙业务就绪状态 */ },
  onAccessPoint: ap => { /* 接收扫描行，保留 ap.ssid_b64 */ }
});

// deviceId 来自本机 App 的 BLE 扫描结果；停止该页面的扫描后连接。
const capabilities = await ble.connect(deviceId);
const list = await ble.scan();            // 发单字节 X，等完整 scan_done
const networkState = await ble.status();  // 扫描结束后再查询

// 本版 capabilities.connect === false，应禁用联网提交按钮。
// 断线后按用户操作或页面策略调用：await ble.reconnect(deviceId)
// 页面退出时释放：
await ble.dispose();
```

App 需自行处理蓝牙权限、设备选择、扫描启停和页面生命周期；本目录不包含完整移动 App。多个页面不应同时创建连接或竞争同一 BLE 对象。原生 App 为本次对接目标，H5 不作为本版支持承诺。

本地软件测试：

```text
node --test test-vela-provision.mjs
```

API 依据：[DCloud BLE 官方文档](https://uniapp.dcloud.net.cn/api/system/ble.html)。本适配器使用有响应的串行写入和不超过 20 字节分片；读取、通知均通过特征值变化监听处理。

## 10. 固件与复现边界

本次板端镜像：`rk3576_radio_id36/nuttx.bin`

SHA-256：`8d53a8cd62b09bea20c4d2d4905c31fe14a0277f0c600914f59a3d189839ab56`

源码冻结目录：`candidate-id36`。BLE 主机补丁链：id28 → id29 → id30 → id34 → id35。id36 修正应用层终止通知与 busy 状态的发布顺序。

在当前树中，ATT/断线事件和自定义通知在同一 LPWORK 线程串行执行，Wi-Fi 扫描在单独任务执行。移植到其他构建配置时必须保留这一约束，不能只复制 GATT 表就认为完成驱动集成。

本次只做 RAM 启动，没有刷写 eMMC，没有驱动云台，没有向远程仓库提交。该无线验证镜像不等于已经合并人脸跟随、三视角拍照和完整应用的最终比赛镜像；这些已确认功能的源码与既有证据保留。

Bluetooth MTU 修复依据：[Bluetooth ATT 规范](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/attribute-protocol--att-.html)。板端按本地缓冲能力协商 MTU，并修正 ATT command 位掩码，已用真实 Windows 客户端和边界测试验证。
